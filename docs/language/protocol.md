# Protocol schemas

A schema is a Rho file that describes what crosses a link — between a sensor
board and the host that reads it, between that host and a service — rather than
what a program does. It is
written once and generated for both ends, so the two can only disagree if the
schema disagrees with itself.

The output of a schema is not a translation of a program. It is an interface:
fixed bytes for the board, typed values and a handler for the service. It is
generated by its own command, apart from a project's build, because the two ends
are built by different toolchains on different machines.

## Declarations

```rho
module sensor
namespace acme.sensor.v2

enum Health {
    OK = 0
    DEGRADED = 1
    FAILED = 2
}

message Reading {
    timestamp_ms: u32
    temperature_c: f32
    humidity: f32
    health: Health
}

rpc SetInterval {
    request {
        sensor_id: u8
        interval_ms: u16
    }
    response {
        accepted: bool
        actual_ms: u16
    }
}
```

- **`namespace a.b.vN`** names the schema and its version. The version is the
  number in the last component, or 1, and it is written into every message.
- **`enum`** values are written, not counted. A wire protocol numbers its values,
  and a reader can only trust a number it can see.
- **`message`** is an ordered set of fields. It is a struct that makes a promise
  a struct does not: a byte layout and a version.
- **`rpc`** is a request and a response, each a set of fields. They become two
  messages, `SetIntervalRequest` and `SetIntervalResponse`.

`message` and `rpc` are contextual: they name a declaration only where one
begins, so a field or a variable may still be called one. A Rho program may not
declare an `enum`, `message` or `rpc`; the type checker refuses them and says
that they belong to a schema.

## The wire

A message is its version byte and its fields in declaration order, each at a
fixed width. Scalars are little-endian, a `bool` is one byte, an enum is a
32-bit value, a bare `string` is 64 bytes, a nested message is its own version
byte and fields, and an array (`u8[16]`) is its elements end to end.
`Reading` above is 17 bytes: the version, three 4-byte fields and the enum.

Little-endian is not the host's byte order but the schema's, so a big-endian
board and a little-endian one read each other's messages. The C side reads and
writes into a buffer the caller owns and allocates nothing.

A message that contains itself cannot be packed and is reported where it is
found.

## Generating

```sh
# C for the board: protocol.h/.c (the bytes)
rho protocol generate --target c --out build/protocol/c schemas

# ...and protocol_bus.h/.c, the rpc transport over a runtime's event bus. The bus's
# own types and functions come from a binding the runtime's platform ships, so
# name one: a file, or a platform whose plugin carries it.
rho protocol generate --target c --platform acme --out build/protocol/c schemas
rho protocol generate --target c --bus bindings/c-bus.yml --out build/protocol/c schemas

# Go for the service: protocol.go
rho protocol generate --target go --out build/protocol/go --package sensor schemas

# Rho for a host program written in Rho: protocol.rho, included from the program
rho protocol generate --target rho --out src/sensor schemas/sensor.rho
```

Without `--out`, the files go to `build/protocol/<target>`. The command prints
the path of each file it wrote.

Every `.rho` under the given paths is read into one schema, so messages may live
in one file and rpcs in another.

### The C side

`protocol.h` carries a `<NAMESPACE>_SCHEMA_VERSION` macro, a `typedef enum`
per enum (`HEALTH_OK` …), a `__attribute__((packed))` struct per message, a
`<NAME>_WIRE_SIZE` macro (`READING_WIRE_SIZE`), and
`Name_serialize(value, out, capacity)` / `Name_deserialize(data, length, out)`
over a caller's buffer. Serialize returns the bytes written, or 0 when the
buffer is too small. Each rpc also gets its request and response event ids and
a handler type (`SetInterval_handler`). `protocol_bus.h` carries, per rpc, a
`publish_request`/`publish_response` and a `subscribe`/`unsubscribe` over the
runtime's event bus (the functions the `protocol-bus-c` binding names), so a
board's handler is reached by an event rather than a call.

### The Go side

`protocol.go` carries `SchemaVersion`, a named type and typed constants per enum
(`HealthOK` …), a struct per message with `json` tags and a `<Name>WireSize`
constant, and `MarshalBinary`/`UnmarshalBinary` that write the same
little-endian bytes the C side reads. Each rpc gets a `<Name>Func` handler type
and a `Register<Name>(mux, path, handler)` that puts the handler on an
`http.ServeMux`. The request and response are JSON over HTTP.

### The Rho side

`protocol.rho` is a Rho module, named after the namespace, that a program
`include`s. Each message becomes a `struct` and three functions: `reading_marshal`
and `reading_unmarshal`, written field by field in the same little-endian order
through the {ref}`text built-ins <language/builtins>`, and `reading_valid`,
which rejects a payload that is short or of another schema version. An enum
becomes `u32` constants (`HEALTH_OK` …), because a Rho program has no enum and the
wire carries a 32-bit value.

Given a framing — `--transport FILE`, or `--platform NAME` for the
`protocol-transport-rho` binding its integration plugin provides — it also carries
the transport. A framing file is Rho: its lines are copied into `protocol.rho`
with `@P@` replaced by the namespace prefix (`acme_sensor_v2`), and lines that
begin with `#` are the binding's notes and are dropped. So a Rho host program
speaks the same framing a board's transport library does, from one description
rather than from a second implementation that must be kept in step. The
toolchain has no framing of its own; without one only the payloads are
generated, and the program decides what each message id means.

## Known limitations

- **No arrays on the Rho side.** A message with an array field generates C and
  Go, and the Rho target refuses it: an array cannot be a Rho struct field yet.
- **`string[N]` is read two ways.** The C codec writes `N` bytes, but the wire
  size and the Go struct treat it as `N` strings of 64 bytes each, so the two
  sides disagree. For text of a fixed length, use `u8[N]`, which C and Go size
  the same.
